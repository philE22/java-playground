# 선착순 쿠폰 발급

> 관련 이슈: [#1 선착순 쿠폰 발급 API 구현](https://github.com/philE22/java-playground/issues/1)

대량 트래픽 상황에서 **정해진 수량을 초과하지 않고, 중복 없이** 자원을 배분하는 문제를 다룬다.
동시성 제어 방식(DB 락 / Redis 원자연산)을 비교하는 것이 이 패키지의 실습 목표다.

---

## 1. 요구사항

### 배경

블랙프라이데이 프로모션으로 **선착순 100,000명**에게 할인 쿠폰을 발급한다.
오픈 시각 정각에 트래픽이 집중되며, 초과 발급 / 중복 발급이 발생해서는 안 된다.

### 용어

| 용어 | 정의 |
|---|---|
| 쿠폰(Coupon) | 발급 대상이 되는 프로모션 정의. 총 수량·기간을 가짐 |
| 발급 이력(CouponIssue) | "누가 어떤 쿠폰을 언제 받았는가" 1건의 기록 |
| 재고 | 총 수량 − 발급 완료 건수 |

### 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 사용자는 쿠폰 ID를 지정해 발급을 요청할 수 있다 | 필수 |
| FR-02 | **1인 1매**. 이미 발급받은 사용자의 재요청은 실패 처리한다 | 필수 |
| FR-03 | 총 발급 수량을 **단 1건도 초과할 수 없다** | 필수 |
| FR-04 | 이벤트 기간(시작~종료) 밖의 요청은 거부한다 | 필수 |
| FR-05 | 발급 성공 시 발급 이력이 남고, 조회할 수 있다 | 필수 |
| FR-06 | 사용자는 자신의 발급 결과를 조회할 수 있다 | 필수 |
| FR-07 | 남은 수량을 조회할 수 있다 (실시간일 필요 없음, 지연 허용) | 선택 |

### 비기능 요구사항

| ID | 요구사항 |
|---|---|
| NFR-01 | 오픈 순간 동시 요청 10,000 TPS를 가정 |
| NFR-02 | 발급 성공 응답 p99 500ms 이내 |
| NFR-03 | **다중 인스턴스(scale-out) 전제.** JVM 단위 락(`synchronized`)만으로는 충족 불가 |
| NFR-04 | 동시성 검증 테스트 코드 필수 |
| NFR-05 | 실패 요청도 원인을 구분할 수 있어야 함 (소진 / 중복 / 기간외) |

### 범위 밖

로그인·인증, 쿠폰 **사용(소진) 처리**, 관리자 쿠폰 등록, 발급 알림 발송

## 2. API 스펙

### 발급 요청

```http
POST /api/coupons/{couponId}/issue
X-USER-ID: {userId}
```
```json
201 Created
{ "issueId": 1, "couponId": 1, "userId": 100, "issuedAt": "2026-11-29T00:00:01" }
```

### 내 발급 이력 조회

```http
GET /api/coupons/{couponId}/issues/me
X-USER-ID: {userId}
```
```json
200 OK
{ "issued": true, "issuedAt": "2026-11-29T00:00:01" }
```

### 잔여 수량 조회

```http
GET /api/coupons/{couponId}/stock
```
```json
200 OK
{ "couponId": 1, "totalQuantity": 100000, "issuedCount": 42310 }
```

### 에러 정책

| 상황 | HTTP | code |
|---|---|---|
| 수량 소진 | 409 | `COUPON_SOLD_OUT` |
| 이미 발급받음 | 409 | `ALREADY_ISSUED` |
| 이벤트 기간 아님 | 400 | `NOT_IN_EVENT_PERIOD` |
| 존재하지 않는 쿠폰 | 404 | `COUPON_NOT_FOUND` |

> 인증은 범위 밖이므로 `X-USER-ID` 헤더로 사용자를 식별한다.

## 3. 데이터 모델

```
coupon
  id, name, total_quantity, issued_count, started_at, ended_at

coupon_issue
  id, coupon_id, user_id, issued_at
  UNIQUE (coupon_id, user_id)   ← 애플리케이션 로직이 뚫려도 DB가 최종 방어선
```

## 4. 인수 조건 (AC)

- [ ] 재고 100, 동시 요청 1,000 → 성공 정확히 100건, 실패 900건
- [ ] 동일 사용자가 동시에 10번 요청 → 성공 1건
- [ ] 위 테스트 후 `coupon_issue` 건수 == `coupon.issued_count` (불일치 없음)
- [ ] 이벤트 시작 전 / 종료 후 요청 → 400
- [ ] 실패 시 응답 code로 원인 구분 가능

## 6. 검토할 동시성 제어 방식

| 방식 | 개요 | 예상 트레이드오프 |
|---|---|---|
| `synchronized` | JVM 단위 락 | 단일 인스턴스에서만 동작. NFR-03 위배 → **반례용으로만 사용** |
| 비관적 락 (`SELECT FOR UPDATE`) | 쿠폰 행을 잠금 | 확실하지만 직렬화되어 처리량 저하 |
| 낙관적 락 (`@Version`) + 재시도 | 충돌 시 재시도 | 경합이 심하면 재시도 폭증 |
| DB 유니크 제약 | `(coupon_id, user_id)` 위반으로 중복 차단 | 중복은 막지만 **수량 초과는 못 막음** |
| Redis `INCR` / `DECR` | 원자적 카운터로 재고 선점 | 빠름. Redis-DB 간 정합성 관리 필요 |
| Redis `SET` 자료구조 | 발급자 집합으로 중복 판정 | 메모리 사용량 고려 |

기존 실습 참고: [`dblock`](../dblock) (비관적/낙관적 락), [`redis`](../redis)
